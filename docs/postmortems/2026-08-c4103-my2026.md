# Postmortem — C-4103-my2026.xls truncado (Volvo Finance sin ER en 202605)

- **Fecha del incidente**: descubierto 2026-07-31, resuelto 2026-08-01
- **Severidad**: Media-Alta (dashboards en produccion mostrando "—" para 4 EDPYMEs completas)
- **Duracion del bug en prod**: ~5 semanas (desde 2026-06-30 hasta 2026-08-01)
- **Detectado por**: usuario final (Gustavo) al revisar informe de Volvo Finance
- **Autor del postmortem**: agente + Gustavo

---

## 1. Resumen ejecutivo

- **Sintoma**: Volvo Finance, Financiera Confianza, Caja Arequipa, CRAC Los Andes
  mostraban "—" en Utilidad/ROE/ROA/PE al cierre May 2026 en `/dashboard/informe`.
  Solo Volvo Finance fue el reporte inicial; investigacion mostro que 4 EDPYMEs
  completas estaban afectadas (Alternativa, Santander Consumo, Vivela, Volvo).
- **Root cause tecnico**: SBS publico `C-4103-my2026.xls` truncado (75,776 bytes vs
  ~290,000 bytes de otros meses). El archivo tenia solo el sheet `bg_edp` (balance),
  faltaba `gyp_edp` (resultados). El importer lo proceso sin excepcion, marco como
  `procesado` con 1,368 filas (vs 2,322 esperadas), y quedo cacheado en disco.
- **Root cause organizacional**: el pipeline confia en la primera publicacion de SBS
  y no tiene mecanismo para invalidar caches locales cuando SBS re-publica.
- **Impacto real**: ~5 semanas sin data ER para 4 EDPYMEs, invisible al operador
  hasta que un usuario final lo noto en el dashboard.
- **Tiempo de resolucion**: 1 dia end-to-end (diagnostico + fix estructural + recovery).

## 3. Root cause — los 5 whys

1. **Por que Volvo mostraba "—"?**
   → Su ER de 202605 no estaba en `marts.mv_eeff_resultados_ancho`.
2. **Por que?**
   → El importer proceso solo el sheet `bg_edp`, no `gyp_edp`.
3. **Por que?**
   → El archivo fisico tenia solo `bg_edp` (75KB truncado por SBS).
4. **Por que el pipeline no lo detecto?**
   → El importer validaba "al menos un sheet reconocido", no "ambos sheets requeridos".
5. **Por que el archivo se quedo cacheado durante 5 semanas?**
   → `skip_if_exists=true` por default en el scraper, sin re-validacion de hash/tamanio
   contra ultima descarga exitosa.

**Raiz ultima**: el pipeline confia ciegamente en la primera publicacion de SBS
y no tiene mecanismo para invalidar caches locales cuando la fuente re-publica.

## 4. Lecciones por dominio

### 4.1. Ingesta

| Leccion | Consecuencia | Control agregado |
|---|---|---|
| SBS re-publica silenciosamente — no es un caso raro | Un archivo bajado hoy puede diferir del de manana bajo el mismo URL | `force_redownload` en `admin.sync_jobs` (V135) |
| `skip_if_exists=true` es peligroso cuando la fuente no promete inmutabilidad | Cargas parciales quedan cacheadas para siempre | Guard estatico de sheets requeridos + detector post-ingest |
| Cargas parciales son peor que fallos — el operador ve "procesado" y no sospecha | Data quality degrada invisiblemente | `raw.detect_partial_ingest()` compara vs promedio historico |
| Un archivo puede ser valido para el parser pero incompleto en negocio | Silencios costosos en dashboards downstream | Validacion estructural (ambos sheets EEFF) en importer |

### 4.2. Deploy

| Leccion | Consecuencia | Accion |
|---|---|---|
| `git pull` en el host != codigo nuevo en el contenedor | El binario Python esta en la imagen Docker | Necesita **rebuild** (no solo restart) en EasyPanel |
| Cron jobs pueden correr con codigo pre-deploy | Sync job #807 corrio 03:00 y "completo" sin ejecutar el `--force` nuevo | Sync jobs deberian registrar el hash del codigo que los proceso |
| No hay verificacion automatica de que un deploy realmente aplico | Descubrimos post-hoc que `grep force_redownload = 0` en el binario | Agregar `aibenchef --version` que imprima commit SHA embedded |

### 4.3. Deteccion

| Leccion | Consecuencia | Control agregado |
|---|---|---|
| Sin baseline "lo que se espera", no podes detectar lo que falta | Volvo paso desapercibido 5 semanas | `admin.expected_files_baseline` (V136) |
| `pg_stat_all_tables.last_autoanalyze` no distingue refresh manual de vacuum automatico | No sabias si tus MVs estaban actualizadas o solo vacuumeadas | `admin.mv_refresh_log` append-only (V137) |
| Raw y marts pueden divergir invisiblemente (delete en raw sin refresh de MV) | La UI muestra data cacheada mientras raw ya cambio | `admin.check_raw_marts_reconciliation()` (V138) |
| La UI es el mejor detector | El usuario disparo el ticket, no los logs | Dashboard `/admin/data-quality` con Score 0-100 |

### 4.4. Recovery

| Leccion | Consecuencia | Accion |
|---|---|---|
| DELETE sin backup es peligroso, aunque el archivo este disponible en fuente | Si SBS tambien hubiera perdido el archivo, se pierde data para siempre | Antes de DELETE en raw, hacer `pg_dump` de las filas afectadas |
| SSH + docker exec es el ultimo recurso que salvo el dia | Sin acceso shell, dependias del deploy | Documentar acceso SSH + backup del `.ssh/` en KeePass o similar |
| Conexiones largas se caen (SSH timeout, psql idle) | El refresh se aborto dos veces | Correr operaciones largas con `nohup` + `tmux`, o via SQL directo desde adentro de la DB |
| CLI viejo puede hacer el trabajo si se le remueve el cache | El fix se hizo sin deploy nuevo | Cuando el codigo nuevo no esta desplegado, `rm archivo + DELETE row + scrape` funciona con cualquier version |

### 4.5. Tests y calidad

| Leccion | Consecuencia | Control agregado |
|---|---|---|
| Todo root cause deberia agregar un test de regresion | Sin test, el bug puede volver silencioso | 8 tests nuevos (3 unit + 5 integration) que fallarian sin V135 |
| Fallar rapido y explicito es mejor que procesar parcial | El importer "completaba con 0 rows" en vez de gritar | `ValidationError` explicito si falta sheet requerido |
| Detectores nuevos deben validarse contra el caso real que motivo su creacion | Un detector que "compila" pero no detecta el bug es peor que nada | Verificamos `detect_partial_ingest` sobre C-4103-my2026.xls -> devolvio `ok=false ratio=0.59` |

## 5. Anti-patrones a evitar

1. "Esta procesado sin error, entonces esta bien" — un ingest exitoso no significa data completa.
2. `skip_if_exists=true` sin invalidacion por hash — asume que las fuentes son inmutables.
3. Un solo tipo de check — hacen falta completeness AND freshness AND consistency AND ingest quality en simultaneo.
4. Refresh manual sin log persistente — se pierde trazabilidad.
5. Solo alertar en severity=critical — warnings tempranos son la mejor deteccion (ver `ratio=0.59` vs threshold 0.60 — casi ok, pero era el bug real).
6. Deploy = git pull en el host — con Docker, deploy debe ser rebuild.
7. Confiar en el UX manual para detectar bugs de data — el usuario final es la ultima defensa, no la primera.
